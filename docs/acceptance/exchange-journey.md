# Exchange journey: second-sector schedule change with a paid seat

Status: acceptance mapping, 3 November 2026. Branch `claude/exchange-journey-acceptance`, based on `349c619` (PR #236 head).

The journey the owner asked for, after comparing the servicing flows of Emirates, flydubai, Lufthansa and Turkish Airlines:

> A passenger books two segments and pays a seat fee; the second segment's schedule changes. The assistant/servicing path calls `searchOffers` then `quoteExchange` and shows the affected segment, the price difference and currency, the fate of the seat fee and the offer expiry; the server binds the passenger's consent to the offer version and amount; `commitExchange` runs through the order service with a scoped capability; if the network drops after the passenger is saved and before the payment result is known, the resume path queries the original operation before any new charge or issuance; afterwards the first segment's coupon is still valid, the second segment's old coupon is voided and a new one issued, the seat was moved or its fee refunded, and an accountant can trace the difference to the provider receipt and the settlement statement.

Evidence produced by this branch:

- `server/__tests__/exchange-journey-acceptance.test.ts` — the journey plus the nine acceptance properties (a)–(i), on the `transactionMemory` fixture with the Stripe boundary mocked (no provider calls). Runs in `pnpm test`.
- `scripts/acceptance/paid-sector-exchange.ts` — the same journey against an empty disposable MySQL through the real routers, signed synthetic webhooks and the lost-acknowledgement replay (`EXCHANGE-SECTOR-01` in `scripts/acceptance/integration-remediation.ts`, run by `production-gates.yml`). Extended here with the consent binding and a consent-mismatch refusal.

Vocabulary: the owner's `searchOffers` / `quoteExchange` / `commitExchange` are not procedure names in this codebase. The table below gives the procedures that implement each step today.

### Trace id versus idempotency key

Verified, not conflated:

- Trace: W3C `traceparent` per HTTP request (`server/_core/trace.ts`), new span per attempt, stored on every outbox event (`traceId`, `spanId`). Test: the quote, commit and settlement attempts carry three different trace ids.
- Idempotency: the quote command uses the client's `idempotencyKey` in scope `order.paid.service` (`withTransactionalIdempotency`); the provider charge uses `order-checkout:<checkoutRequestId>`, a UUID written once per modification and reused by every retry; the `payments` row uses `stripe:<paymentIntentId>`. Test: two checkout attempts in two traces send one identical Stripe idempotency key.

## Fixes made in this branch (within scope)

1. **Consent bound server-side** (`order-servicing.service.ts`, `order-service-checkout.service.ts`, `routers/ndc.ts`, `routers/payments.ts`, `contracts/modifications.ts`, `order-exchange-context.service.ts`, `ModifyBookingDialog.tsx`): `quoteVersion` returned and exposed; `consent` required by the client-facing procedures; mismatch refused before any provider call; accepted consent stored on the modification. Older clients that send no consent, or consent of another shape, are refused with a clear message (test (d)).
2. **Unsupported stored quote version is a servicing precondition, not a crash** (`parseServicingPlan`): `planSchema.parse` inside the settlement transaction used to throw a ZodError, which `settleVerifiedPayment` does not classify, so the webhook would have returned 500 and Stripe would have retried a collection that can never apply. It is now `OrderServicingUnavailable`, so the collection is retained for review.
3. **Audit entry on denied cross-owner servicing** (`audit.service.ts` `auditServicingAccessDenied`, wired in quote, checkout, confirm, cancel, context and the payments router): written after the refused transaction rolls back, so the record survives; the caller's message is unchanged and generic.

4. **Quote idempotency key is client-owned and required** (idempotency audit F2, `booking-modification.service.ts`, `routers/modifications.ts`): the service used to fall back to `randomUUID()` when the client sent no key, so a retry after a lost response was a new command. The charge itself was never at risk (it is keyed by `checkoutRequestId`), but the quote retry was not idempotent. The key is now required (8–100 characters) at the router and the service.
5. **Legacy modifications cannot start an unkeyed provider checkout** (idempotency audit F1, `routers/payments.ts`): rows without a `servicingPayload` have no frozen claim (saved request body, invoice fingerprint, consent) and the old branch created a new Stripe session on every call without an idempotency key. The branch is removed; such a modification is refused with "request a new quote". New quotes always carry the frozen claim.

## Findings outside this workstream (not changed)

- **No seat-fee refund path on exchange.** When no equivalent paid seat exists on the replacement, the quote is refused for operator review. A refund-the-fee alternative (EMD refund) would belong with the fare-components/EMD work.
- **No bearer capability for servicing.** Scope is enforced by owner, tenant and the consent-bound quote under row locks. If the owner wants a transferable, time-boxed capability (e.g. for an agent acting for a passenger), `self-service-capability.service.ts` is the pattern; that is an authorization design decision.
- **Resume path does not query the provider session.** It replays the saved request under the provider's idempotency key and refuses after 23 h. Reconciliation of a session whose acknowledgement was lost for longer is left to `stripe-reconciliation.service.ts` (dry-run exists).
- **`exchangeContext` and `comparePayoutEvidence` use SQL joins**, which the `transactionMemory` fixture cannot execute; they are covered by `e2e/hardening-journeys.spec.ts` and `scripts/acceptance/paid-sector-exchange.ts` on MySQL, and their join predicates are asserted key-by-key in tests (c) and (i).
- **Revenue recognition at exchange.** Nothing is recognised at exchange time; `revenue-accounting.service.ts` reports `deferredRevenue: null` deliberately. Test (f) proves the cash period and the open coupon; the IFRS 15 treatment of the unflown coupon is the loyalty/revenue workstream's.
- **Manifest and crew views** are derived from `booking_segments.flightId` (`flightBookingCondition`), so they follow the exchange; `generateFlightManifest` is demo-gated and was not executed here.
- **Migration runner on MariaDB.** `scripts/db/migrate.ts` reads `information_schema.statistics.IS_VISIBLE` (MySQL 8 only). Irrelevant for CI (MySQL 8) but blocks a local MariaDB rehearsal; `drizzle-kit push` worked.
- **Local rehearsal on MariaDB is not possible.** Besides the migration runner, the application issues `SELECT ... FOR SHARE` (`tenant.service.ts`), which MariaDB 10.11 rejects; the acceptance harness therefore only runs on MySQL 8 in CI. The vitest journey and the nine properties ran locally; `EXCHANGE-SECTOR-01` runs in `production-gates.yml`.
