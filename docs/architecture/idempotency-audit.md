# Idempotency keys and trace identifiers: audit of money-moving operations

- **Status:** audit of commit `349c619` (PR #236 head), 3 November 2026, workstream 13.
- **Scope:** every operation that charges, refunds, credits, issues or voids value. For each: the idempotency key (derivation, storage, TTL, scope), the per-attempt trace identifier, how a client retry, a worker retry and a webhook redelivery behave, and the reconciliation that would catch a duplicate. Verified by reading code and the tests named below; nothing here was verified against a live provider.
- **Rule under audit** (from the Turkish Airlines developer-portal finding): a trace or transaction identifier that changes with every attempt must be kept separate from the idempotency key that stays constant for the financial operation; and an assistant may fetch alternatives before it holds a specific authorisation to execute one.

### Follow-up on the findings in section 5

The historical rows below describe the audited revision. The follow-up uses a deterministic fallback for modification quotes (F2), an actor-scoped command receipt for administrative credit (F3), a client intent and atomic receipt for miles redemption (F4), and the reserved invoice number plus a content check for fiscal drafts (F5). The MySQL remediation suite exercises concurrent credit grants, a lost redemption response, conflicting retries and repeated draft creation. These checks run against synthetic records.

## 1. The rule, and where it now lives in code

`server/_core/idempotency.ts` is the shared helper and carries the rule in its header comment:

| API                                  | Purpose                                                                                                                                                                                                                                                           |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `operationKey(scope, naturalKey)`    | Builds `{ scope, key, value: "scope:key" }` from the operation's natural identity only (row ids, provider object ids, a persisted request id). Rejects empty parts, non-integer numbers, unsafe characters and anything over 255 chars (column and Stripe limit). |
| `traceId()`                          | The ambient W3C trace id (`server/_core/trace.ts`) or a fresh one for this attempt. For logs and spans. Never a key, never inside a key, never inside a keyed request body.                                                                                       |
| `providerRequestOptions(key)`        | `{ idempotencyKey, timeout: 15000, maxNetworkRetries: 0 }` for Stripe. SDK transparent retries are off because the caller owns replay.                                                                                                                            |
| `runIdempotentOperation({key, ...})` | Wraps `withIdempotency` from `server/services/idempotency-v2.service.ts`: same key → cached response without re-running; key in progress → `IDEMPOTENCY_IN_PROGRESS`; failed key → retry allowed; each attempt logged with the constant key and its own trace id. |

Two existing mechanisms remain the storage layer and are not duplicated:

- `idempotency_requests` (`drizzle/schema.ts:1496-1530`, unique on `scope + userId + idempotencyKey`) through `withIdempotency` (result cache, in-progress refusal, TTL default 3600 s, `idempotency-v2.service.ts:230-394`) and `withTransactionalIdempotency` (claim row locked `FOR UPDATE` inside the business transaction, response committed with the command, `expiresAt` NULL so the receipt lives as long as the command, `idempotency-v2.service.ts:128-208`).
- `stripe_events` (`drizzle/schema.ts:1286-1304`, primary key = Stripe `evt_` id) for webhook redelivery, and `event_inbox` + `event_deliveries` (`server/services/event-inbox.service.ts:39-223`) for outbox consumers, keyed by `eventId` + consumer.

One consequence of the rule that the audit made explicit: a trace id must **not** be written into the parameters of a Stripe call that carries an idempotency key, because Stripe rejects a replay whose body differs from the first attempt. The frozen `requestPayload` pattern used by booking and split checkout (below) is the correct shape; the trace belongs in the log line and the span, where `server/services/outbox.service.ts:67-82` already records it per event.

## 3. Assistant: fetching alternatives versus executing one

Verified state at `349c619`:

- The assistant router exposes eight procedures, all conversational (`routers/ai-chat.ts`). `getSuggestions` is a read; `selectSuggestion` only flips `booking_suggestions.selected` and returns `{ flightId, cabinClass, price }` (`ai-chat-booking.service.ts:484-530`). Neither the router nor the service imports any booking, checkout, settlement, wallet, voucher, loyalty or refund module. The commit of a booking happens through `bookings.create` under the user's own session with a server-computed amount, never through the assistant.
- Policy and exchange questions are answered locally without the model and without reserving or charging (`:243-313`), already tested in `server/__tests__/ai-chat-passenger-policy.test.ts`.

Added so that a future execute path cannot skip the rule:

- `self-service-capability.service.ts` gains the `assistant-execution` capability kind (10-minute TTL) bound to `userId`, `conversationId`, `suggestionId`, `flightId`, `cabinClass`, `amount` and `offerVersion`, with `assistantOfferVersion()` (SHA-256 over suggestion, flight, cabin, price) and `assertAssistantExecutionAuthorised(token, expected)`: missing → `UNAUTHORIZED`; another user or another alternative → `FORBIDDEN`; a changed amount or offer version → `PRECONDITION_FAILED` so the client fetches alternatives again.
- `server/__tests__/assistant-execution-authority.test.ts` pins both halves: the assistant can list and select an alternative while every money and inventory table stays empty, and no execution can be authorised without a user-bound token for the exact priced offer (kiosk tokens and tampered tokens are refused).

Nothing issues the token yet because nothing executes. When an execute procedure is added, `selectSuggestion` should issue it alongside the selection, and the execute procedure must call `assertAssistantExecutionAuthorised` before any `operationKey` is built.

## 6. How to apply the rule at a new call site

1. Name the operation and its natural identity: `const key = operationKey("refund.issue", [bookingId, paymentIntentId]);`
2. If the provider is Stripe: `stripe.refunds.create(params, providerRequestOptions(key))`, with `params` identical on every attempt (no trace id, no timestamp).
3. If the result must be cached and concurrent attempts refused: `runIdempotentOperation({ key, userId, request: params, run })`; for DB-only commands that must commit with their receipt, `withTransactionalIdempotency`.
4. Log with `traceId()` (or rely on the ambient trace through `createServiceLogger`); never put it in the key or the keyed body.
5. Add a test that calls the site twice and asserts one provider call (or two calls with an identical key and identical body), and one that asserts the key is free of `Date.now()`, `randomUUID()` minted in the call, and trace ids.
