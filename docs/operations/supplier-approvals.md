# Supplier bank changes and internal SAR payout approvals

The airline finance console records an internal decision. No bank instruction, PSP request, ledger settlement, or payment confirmation is created. A supplier UUID identifies a counterparty in the operator's external master; a fresh vault UUID identifies an immutable bank version maintained there. Supply only the last four digits in AIS. The operator must verify the supplier and destination through an independent channel before approval. The reviewer can compare the displayed SHA-256 of the lowercase vault UUID without exposing its value.

1. A tenant-bound finance user opens the supplier and records a change against the displayed bank version. The first version starts at one. A new bank immediately supersedes the old version and its internal payout approvals, even before the new bank is approved.
2. A different finance user reviews the version, last four digits and vault-reference fingerprint and approves the bank. A pending bank cannot receive a payout request.
3. A requester submits an invoice UUID and integer SAR halalas. The checker approves the same invoice, bank version and exact amount. Both the bank editor and the payout requester are ineligible to approve that payout.
4. Open the invoice to see its current status. After a bank change the old receipt remains in history, linked to the superseding receipt. Re-authorization requires bank approval and a new payout request against the new version. An old request ID can reproduce its historical receipt; the review query determines present validity.
5. If a response is lost, retry with the same request ID and body. A different body with that key conflicts. Reload before creating a genuinely new decision. The interface displays the latest 50 decisions.

Each command stores its receipt and audit event in one transaction. Database migration 0058 requires MySQL trigger privileges and installs guards against editing event rows, inserting an event without its profile, or deleting or rekeying a supplier profile. A new profile starts at zero. Each subsequent version advances by one after its superseding bank-change evidence is inserted in the same transaction. Guarded rows are not a substitute for independent backups or restricted DBA access. The integration check in `scripts/acceptance/supplier-finance.ts` exercises the real tRPC contract, separate users and tenants, concurrent replay, role revocation, supersession, and direct attempts to alter the evidence.
