# مخزون درجات الحجز RBD

تضيف هذه الدفعة مخزوناً اختيارياً لكل رحلة ودرجة حجز إلى مسار البيع القائم.
يبقى عداد المقصورة في `flights` السقف الفيزيائي، بينما يقيّد
`flight_fare_class_inventory` ما يمكن بيعه تحت رمز RBD محدد. الرحلات التي لا
تملك صفوف RBD تستمر في مسار المقصورة القديم، ولذلك لا تتغير الحجوزات التاريخية.

## حدود المعاملة

1. يعرض البحث السعة الحية بعد طرح الحجوزات المؤقتة غير المنتهية.
2. عند طلب `fareClassCode` تتحقق خدمة الحجز من شركة الرحلة والمقصورة والرمز، ثم
   تقفل الرحلة وصف المخزون وتكتب `fareClassId` في حجز السعة.
3. في الرحلة متعددة القطاعات يمكن أن يحمل كل قطاع رمزاً مختلفاً، وتُنشأ كل
   الحجوزات المؤقتة داخل معاملة واحدة وبترتيب معرف الرحلة لتقليل التعارض.
4. عند إثبات التمويل تُخصم المقصورة ودرجة الحجز معاً. يؤدي فشل أي ساق إلى تراجع
   المعاملة كاملة. الإلغاء الكامل يعيد العدادين.
5. تبقى الحقول الجديدة قابلة للإفراغ حتى لا يُنسب RBD إلى حجز قديم لم يسجله.

## قيود القبول

- لا تنشئ هذه الدفعة خرائط درجات أو حصصاً افتراضية. يجب على المشغّل تحميل
  `capacity` و`availableSeats` لكل رحلة ودرجة من مصدر إدارة الإيراد المعتمد.
- لا تعتبر أولوية `fare_classes` بديلاً عن ضوابط nesting أو bid-price لدى
  المشغّل. صف الرحلة هو قرار البيع الصريح، والسعة الفيزيائية حد إضافي.
- يرتبط عرض تغيير القطاع بدرجة القطاع الأصلي وسعره المعتمد على الرحلة البديلة.
  يُحجز المقعد ضمن المقصورة والدرجة، ويعيد تنفيذ التبديل مخزون القطاع القديم.
  عند الاضطراب يخصم محلّل الاستعادة القيدين لكل مجموعة. تتطلب إعادة توزيع الدرجات
  بين القطاعات أو تغيير المقصورة خريطة معتمدة.
- الاختبارات المحلية لا تثبت مزامنة مزوّد مخزون أو قبول GDS/NDC خارجي.

تصف IATA الانتقال الجاري من درجات الحجز وقواعد الأسعار التقليدية إلى Offers &
Orders. لذلك صُمم هذا العمل كجسر متوافق مع النظام الحالي، وليس كسجل طلب حديث
نهائي. تمت مراجعة صفحة IATA الرسمية في 3 نوفمبر 2026.

- [IATA Airline Retailing](https://www.iata.org/en/programs/airline-distribution/retailing)

## المخطط المخزّن في الترحيل 0059

- جدول `flight_fare_class_inventory` مع مفتاح فريد `(flightId, fareClassId)`
  وحقلي `capacity` و`availableSeats`.
- `inventory_locks.fareClassId` مع فهرس مركب.
- `bookings.fareClassId` و`booking_segments.fareClassId` مع فهارس.

يجب أن يضيف الترحيل القيود التالية بعد تنظيف البيانات، وهي عدم سلبية السعة
والمتاح، وألا يزيد المتاح على السعة.

## تحميل تخصيص موثّق من المشغّل

يقرأ الأمر ملف JSON يحدّد مرجع القرار والمستأجر والناقل. مثال اصطناعي لصف واحد:

```json
{
  "reference": "SYNTHETIC-RM-01",
  "tenantId": 1,
  "airlineId": 1,
  "rows": [
    {
      "flightId": 20,
      "fareClassId": 4,
      "cabin": "economy",
      "expectedCabinAvailable": 10,
      "capacity": 4,
      "availableSeats": 3
    }
  ]
}
```

شغّل `node --import tsx scripts/db/provision-rbd.ts allocation.json` مع اتصال قاعدة البيانات المعنية. تعرض المعاينة التغييرات المقترحة وبصمة التخصيص. بعد مراجعة الصفوف، يُطبّق المشغّل القرار بالأمر نفسه مع `--apply=<digest>`. تُراجع سعة المقصورة تحت قفل الرحلة. يُرفض اختلاف السعة قبل الإدخال، وتُلغى الدفعة كاملة عند فشل أي صف. تكرار التطبيق يحفظ رصيد الفئة الحالي بعد المبيعات. تبقى حجوزات المقصورة التاريخية دون تعيين إلى فئة مستنتجة.
