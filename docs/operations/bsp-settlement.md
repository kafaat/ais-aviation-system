# تسوية BSP: RET صادر وHOT وارد ومطابقة

## اتجاه البيانات

في مسار IATA NDCLink (ومع IFG حين تُعدّ المنصة الملف) **ترسل** شركة الطيران تقرير المبيعات اليومي بصيغة DISH RET إلى مركز معالجة بيانات BSP، و**تستلم** منه ملف الفوترة الموحّد HOT. التصميم السابق في AIS عامل HOT كمُخرَج؛ هذه الدفعة تصحّح الاتجاه: أُزيلت `bspReporting.exportHOT`، وأُضيف مسار `bspSettlement` مع وحدة استيعاب جديدة في `server/services/bsp/`.

| الخطوة         | المصدر                                          | الوجهة                                       |
| -------------- | ----------------------------------------------- | -------------------------------------------- |
| RET (مبيعات)   | AIS: `bsp_ret_files` / `bsp_ret_lines`          | مركز معالجة BSP عبر محوّل النقل في الاتفاقية |
| HOT (فوترة)    | مركز معالجة BSP                                 | AIS: `bsp_hot_files` / `bsp_hot_lines`       |
| التحويل البنكي | كشف حساب البنك (CSV)                            | AIS: `bsp_bank_remittances`                  |
| بوابة المطابقة | الدفتر `financial_ledger` × RET × HOT × التحويل | `bsp_reconciliation_runs` / `_items`         |

## تخطيط السجلات (`server/services/bsp/dish-layouts.ts`)

كل سجل بعرض ثابت 255 حرفاً، يبدأ باسم السجل في DISH (معرّف الرسالة + رقم السجل) وتحمل عناصره رموز DISH (TRNN، TRNC، TDNR، AGTN، DAIS، COBL، TMFT/TMFA، COAM، FPTP/FPAM). المبالغ أعداد صحيحة بالوحدة الصغرى والعملة بصيغة `SAR2` (عدد الكسور الضمنية). الاستردادات تُبلغ بمبالغ موجبة تحت `TRNC=RFND` وتُطرح في مجاميع التحكم.

| السجل | الدور                                                                                          | في RET | في HOT |
| ----- | ---------------------------------------------------------------------------------------------- | ------ | ------ |
| BFH01 | ترويسة الملف (الفترة، REVN، TEST/PROD، البلد، التسلسل)                                         | ✓      | ✓      |
| BCH02 | ترويسة المعاملة (TRNN، TRNC، AGTN، DAIS، CUTP)                                                 | ✓      | ✓      |
| BOH03 | ترويسة مكتب الوكيل                                                                             |        | ✓      |
| BKT06 | هوية المستند (TDNR، CPUI، PXNM، STAT، RTDN)                                                    | ✓      | ✓      |
| BKS30 | مبالغ المستند (COBL، حتى 3 ضرائب، TDAM)                                                        | ✓      | ✓      |
| BKS39 | العمولة (COTP، CORT، COAM)                                                                     | ✓      | ✓      |
| BKP84 | وسيلة الدفع (FPTP، FPAM؛ لا يُملأ رقم الحساب أبداً)                                            | ✓      | ✓      |
| BOT93 | مجاميع المكتب والتحويل لكل وكيل                                                                |        | ✓      |
| BCT95 | مجاميع التحكم لكل عملة (العدد، الأجرة، الضريبة، العمولة، الصافي بإشارة، المبيعات، الاستردادات) | ✓      | ✓      |
| BFT99 | ذيل الملف (عدد السجلات والمعاملات وسجلات BCT95)                                                | ✓      | ✓      |

**حدود المصدر.** مجموعة السجلات وعرضها ورموز العناصر تتبع دليل IATA DISH، وهو موزّع على المشاركين في BSP فقط. مواضع الحقول في الجدول هي **ملف تعريف AIS** ويجب اعتمادها مقابل إصدار DISH المسمّى في مواصفة الربط المؤكدة قبل أي إرسال. المولّد والمحلّل مدفوعان بالجدول، فاستبدال التخطيط المعتمد لا يمسّ منطق التوليد أو المطابقة. ملفات الاختبار في `server/__tests__/fixtures/bsp-hot.ts` مُركّبة من هذا الجدول وليست ملفات BSP حقيقية.

## RET الصادر

`bspSettlement.generateRet` يجمع من `financial_ledger` قيود `charge`/`refund`/`partial_refund` التي يقع `transactionDate` فيها داخل نافذة الإبلاغ، ويقتصر على حجوزات قناة الوكلاء (`agent_bookings`)؛ المبيعات المباشرة تُعدّ وتُستثنى. يُنشئ مستنداً لكل راكب يحمل رقم تذكرة محلي (13 رقماً) ويحتسب العمولة بنسبة سجل الوكالة. تُخزَّن كل نسخة مع SHA-256 والحالة `generated → transmitted → accepted | rejected`، وتُعاد قراءتها وتدقيق مجاميعها قبل التخزين وقبل الإرسال.

**نافذة الإبلاغ** تُقطع بالتوقيت المحلي لبلد BSP (`server/services/bsp/reporting-period.ts`): تاريخ الإبلاغ D يغطي من وقت القطع في D−1 حتى وقت القطع في D (غير شامل)، بحساب UTC خالص مع Intl ليحترم التوقيت الصيفي ولا يتأثر بمنطقة الخادم.

**مكونات الأجرة.** يقرأ التوليد الأساس والضرائب والرسوم عبر الواجهة `FareComponentSource` (`server/services/bsp/fare-components.ts`). حتى يصل جدول `booking_fare_components` من مسار مكونات الأجرة، يعود المصدر الافتراضي بـ `null` ويُستخدم توزيع متساوٍ لمبلغ القيد بلا تفكيك ضريبي؛ تُعلَّم هذه الأسطر `booking_total_fallback` ويُرفض إرسال أي ملف يحويها. لا يُخترع تفكيك ضريبي.

## HOT الوارد

`bspSettlement.ingestHot` يخزّن الملف كما ورد مع بصمته (البصمة فريدة، فلا تكرار)، ويحلّله إلى صفوف منمّطة (`bsp_hot_lines`) مع صافي كل مستند (الأجرة + الضريبة − العمولة، سالب للاسترداد) ومجاميع المكتب والبلد. أنواع السجلات غير المعروفة تُسجَّل تحذيراً وتُتجاوز؛ السجل المعروف المعطوب أو الذيل المخالف للتفاصيل يُرفض الملف كله.

## التحويل البنكي

`bspSettlement.importBankStatement` يستورد CSV بأعمدة `date` و`amount` و`reference` (واختيارياً `currency` و`counterparty`). لا تُقرأ أرقام الحسابات. تمنع بصمة الكشف تكرار الاستيراد.

## بوابة المطابقة

`bspSettlement.runReconciliation` يطابق كل بيع واسترداد في الدفتر بالمستند مع (أ) سطر RET المُبلَّغ، (ب) سطر HOT، (ج) تحويل الفترة. لأن البنك يحوّل صافياً واحداً للفترة لا لكل تذكرة، تُقرَّر تغطية التحويل على مستوى الفترة (مجموع إيداعات الفترة = صافي HOT).

| التصنيف              | الشرط                                               |
| -------------------- | --------------------------------------------------- |
| `matched`            | سطر HOT موجود، الصافي مطابق، والتحويل يغطي صافي HOT |
| `amount_mismatch`    | سطر HOT موجود بصافٍ مختلف عن المتوقع من الدفتر      |
| `missing_in_hot`     | مستند في الدفتر لا يقابله سطر HOT                   |
| `missing_remittance` | مطابق في HOT لكن إيداعات الفترة لا تساوي صافي HOT   |
| `unexpected_in_hot`  | سطر HOT (أو سطر مكرر) لا يقابله مستند في الدفتر     |

تظل حالة التشغيل `open` وتُحجب «التسوية مكتملة» حتى يصير كل بند `matched` أو يُسجَّل له تصرف مع سبب (`dispositionItem`، ≥5 أحرف، يُحفظ مع المنفّذ والوقت ولا يُحذف). خطتا ARC و«أخرى» موسومتان بديلاً غير منفذ وتُرفضان في التوليد والتأكيد والمطابقة برسالة صريحة.

## مواصفة الربط التعاقدي

`settlement_link_specifications`: بلد BSP، خطة التسوية، نوع الربط (`ndclink | ifg | direct`)، إصدار DISH، الرمز الرقمي للناقل، معرّف نظام الإبلاغ، العملة، المنطقة الزمنية، أوقات قطع RET وHOT المحلية، تواريخ النفاذ، وحالة التأكيد (`draft | confirmed | revoked`) مع مرجع تأكيد BSP. التوليد مسموح لمسودة (ويُعلَّم الملف `TEST`)، أما `transmitRet` فيشترط مواصفة **مؤكدة** نافذة في تاريخ الإبلاغ وأن يكون الملف مولّداً تحتها، بلا أسطر بديلة، وبصمته سليمة. أي تعديل يعيد المواصفة إلى مسودة.

## محوّل النقل

`server/services/bsp/ret-transport.ts` يعرّف العقد `RetTransport.transmit(file) → { reference, transmittedAt }`. المحوّل المتاح `file_drop` يكتب الملف في `BSP_RET_DROP_DIR` (بلا كتابة فوق ملف موجود) عند `BSP_RET_TRANSPORT=file_drop`؛ بدون تهيئة يُرفض الإرسال. لا يتصل أي محوّل في المستودع بنظام خارجي؛ يُركَّب محوّل القناة المسمّاة في اتفاقية الربط ويعاد استخدام البوابة نفسها.

## ما يبقى للقبول

اتفاقية ربط BSP موقعة (NDCLink أو IFG أو مباشر) وإصدار DISH المعتمد، واعتماد مواضع الحقول مقابل مواصفة البلد، ومحوّل نقل معتمد، وإقرار قبول RET حقيقي من مركز المعالجة، وملف HOT حقيقي يُستوعب ويُطابَق بإيداع فعلي. سطر الكتالوج: «RET generation and HOT ingestion implemented; transmission and acceptance pending BSP link agreement».
