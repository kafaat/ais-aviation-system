# توحيد قراءة الاستردادات المثبتة

الأساس: `b5b2c0990e6045def2e330be21903c903596d68b`، الإصدار `v1.22.7` بعد دمج #140. هذه المتابعة تخص لوحة الاستردادات وسجلها واتجاهاتها وتصدير الاستردادات؛ لا تغيّر أرصدة أو تصدر طلبات دفع أو تضيف ترحيلة.

## الفجوات المثبتة والإصلاح

كانت الإحصاءات والتصديرات تختار الحجوزات ذات `paymentStatus=refunded` وتجمع إجمالي الفاتورة، وتؤرخ الاسترداد بتاريخ تعديل الحجز. بذلك تغيب الاستردادات الجزئية برسوم والحصص التي اكتمل بعضها فقط. وكانت أخطاء قاعدة البيانات تُستبدل بصفر أو قائمة فارغة.

أصبحت القراءة من قيود `financial_ledger` من نوع `refund/partial_refund` بالريال والمرتبطة بحجز موجود. كل قيد يمثل فرق تسوية مثبتًا؛ ليس بالضرورة طلبًا مستقلًا لدى البنك. المبلغ `DECIMAL` يُحوّل في SQL إلى هللات ثم يتحقق من كونه عددًا صحيحًا آمنًا. يحدد `transactionDate` الفترة الزمنية، ويحفظ `id` هوية القيد حتى لو تغير الحجز أو تعددت دفعاته. لا يُستنتج مال مسترد من إجمالي الفاتورة أو وجود طلب معلق.

| المسؤولية                         | المالك التقني                                    | المستهلكون                                                       |
| --------------------------------- | ------------------------------------------------ | ---------------------------------------------------------------- |
| كتابة قيد الاسترداد               | `payment-settlement.service`                     | دفتر الأموال؛ تستهلكه قراءة التقارير                             |
| القراءة الموحدة للقيود والمبالغ   | `refunds-stats.service`                          | `refunds.getStats/getHistory/getTrends` و`report-export.service` |
| الطلبات المعلقة والمراجعة والرسوم | `split-refund.service` والجداول الدائمة          | إحصاءات الطلبات وقائمة الإلغاء القائمة                           |
| صلاحية المشاهدة والتصدير          | `refunds` و`reports` عبر `adminProcedure`        | لوحة الإدارة وأزرار التصدير                                      |
| إخراج CSV/XLSX/PDF                | `report-export.service` من `getRefundExportRows` | تنزيلات المستخدم الإداري؛ نفس المبالغ والفترة                    |

يبقى الفهرس 152 خدمة: 139 نشطة، 11 متقاعدة وملفان للأنواع. هذه ملكية تقنية؛ لا تحل محل تسمية مسؤول بشري.

## معنى الحقول

- `totalRefunds/completedRefunds`: عدد قيود التسوية، و`totalRefundedAmount` مجموع المبالغ المثبتة بالهللات. `refundedBookings` عدد الحجوزات دون تكرار؛ يُحسب معدل الاسترداد منه لمنع تضخيمه بسبب تعدد الدافعين.
- `pendingRefunds/pendingRefundAmount`: عدد ومبالغ حصص `queued/requesting/pending` المسجلة. لا تضاف إلى الأموال المثبتة.
- `reviewRequiredRefunds/reviewRequiredAmount`: حصص `failed/review_required`. قد تشمل قيدًا سابقًا يحتاج تسوية عكسية موثقة؛ ليست موافقة على صرف مال جديد.
- `retainedCancellationFees`: مجموع الرسوم المثبتة في قرارات الإلغاء مرة واحدة لكل خطة، ويُعرض نطاقها في الواجهة. هذه ليست عملية تحصيل إضافية.
- إجماليات الشاشة تُقرأ من لقطة واحدة بمعاملة `REPEATABLE READ / READ ONLY`. الواجهة تخفي الإجماليات القديمة عند فشل القراءة وتعرض إعادة المحاولة، وتفصل فشل السجل والاتجاهات عن النتيجة الفارغة.

## التواريخ والتصدير

فترات التاريخ المجرد مثل `2026-09-11` تشمل يوم النهاية كاملًا بتوقيت UTC. توقيت ISO الصريح يحتفظ باللحظة المحددة. يستخدم الاستعلام القيمة الزمنية الداخلية عبر `UNIX_TIMESTAMP(TIMESTAMP)` للمقارنة وتجميع أيام UTC، وفق [مرجع MySQL الرسمي](https://dev.mysql.com/doc/refman/8.0/en/date-and-time-functions.html#function_unix-timestamp)، فتتطابق التواريخ في الشاشة والملفات.

تقرأ صيغ التصدير الثلاث الإسقاط نفسه مرة واحدة، وتشمل الكامل والجزئي المثبتين. لا يخلط الملف طلبات لم تُسوّ بعد مع الأموال المستردة. الحد 10000 قيد؛ فحص القيد الإضافي يرفض التصدير الكبير برسالة تضييق الفترة بدل تنزيل ملف ناقص بصمت. يعرض XLSX/PDF عدد القيود والحجوزات والمجموع الفعلي. الفترات الافتراضية موحدة؛ زر اللوحة يرسل آخر 30 يومًا.

أُغلقت أيضًا قابلية تفسير النصوص غير الموثوقة كصيغ عند فتح CSV. تبقى خلايا XLSX النصية قيمًا نصية وليست كائنات صيغ. لا يُظهر عقد سجل اللوحة بريد المالك المخصص للتصدير الإداري.

## أدلة التحقق

- اختبارات الخدمة والملفات تنفذ تحويل الأموال، الإخراج الفعلي عبر ExcelJS/PDFKit، رفض القيم غير الصالحة والتجاوز الصامت، حدود الفترة والصفحات، صلاحية الإدارة وعدم تسريب أخطاء السائق أو حقول البريد.
- اختبارات الواجهة تثبت عرض 75.01 ريال لاسترداد جزئي مستقلًا عن المعلق والرسوم، وإخفاء الأرقام القديمة وإعادة المحاولة عند الخطأ.
- `scripts/acceptance/refund-reporting.ts` يضيف ثلاثة فحوص MySQL حقيقية: مبالغ حصص جزئية وعد الرسوم مرة واحدة، استقلال المال عن تعديل الفاتورة، حدود منتصف الليل وتطابق التصديرات وثبات السجلات، واستبعاد العملة الأخرى وثبات الصفحات. تتغير قيم صناعية داخل القبول ثم تُعاد قبل فحص النسخ الاحتياطية. يصبح القبول 43 فحصًا عند نجاح CI، إضافة إلى ستة فحوص نسخ واستعادة.
- الفحص المحلي الكامل: 1607 ناجحة و241 متجاوزة؛ المتجاوزة تتطلب خدمات غير متاحة محليًا ولا تعد دليل قبول.

كشف القبول الأول أن Drizzle يولد صيغة بدء غير صالحة عند الجمع بين `withConsistentSnapshot` و`read only`. أُبقيت معاملة القراءة فقط بعزل `REPEATABLE READ`؛ تبدأ اللقطة المشتركة بأول SELECT. يستخرج تشخيص الخادم رمز خطأ السائق المغلف دون تسجيل SQL أو القيم، وتتحقق بوابة MySQL من المسار الفعلي.

نجحت الفحوص الـ43 في التشغيل التالي، لكن مؤقت تنظيف الذاكرة في `rate-limit.service` أبقى عملية القبول حية بعد إغلاق MySQL وRedis. أصبح المؤقت غير مانع لانتهاء العملية عبر `unref()`؛ يستمر التنظيف عندما يعمل الخادم، وتنتهي أدوات CLI طبيعيًا بعد إغلاق مواردها. لا يغير الإصلاح حدود الطلبات ولا يرفع مهلة CI ولا يفرض خروج العملية.

## المتبقي

كانت تقارير الإيرادات العامة وتصدير مستودع البيانات الفجوة التالية عند كتابة هذا التقرير. استُكمل توحيد قراءتها في [متابعة التحصيل والتقارير المالية](20260911-posted-financial-reporting.md)، مع عقد v2 يميز الفاتورة والتحصيل والصافي ويصرح بعدم توفر الاعتراف المحاسبي. تبقى مطابقة القيود القديمة ودفتر الاعتراف مرحلتين مستقلتين. لا تدعي هذه المتابعة توحيد المحاسبة العامة أو معالجة السجلات التاريخية الناقصة. الأرصدة بعملات أخرى واستردادات غير مرتبطة بحجز خارج نطاق هذه الشاشة بالريال.

لم تُنفّذ طلبات Stripe حقيقية أو ترحيل/نشر إنتاجي. اكتمل CI الخاص بـ#140، لكن النشر الفعلي على Kubernetes تُخطي لغياب `PRODUCTION_KUBECONFIG`. تبقى بيئة المشغل وقبول المزود وحماية main والملاك البشريون متطلبات خارجية.
