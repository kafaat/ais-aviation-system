### Takeaway

The platform registers 89 tRPC domains spanning shopping/booking, payments, servicing, departure control, loyalty, B2B channels, operations/admin and platform concerns, but the repository's own capability catalog classifies 8 of 19 named capabilities as `demo` (gated off in production) and 4 as `blocked` (no production adapter), and the deep operations modules (GDS, biometric, weight & balance, load planning, multi-region, DR, bag-drop hardware) refuse to run unless `AIS_ENABLE_DEMOS=true` outside production.

## Key question 2: How are orders/bookings/tickets/EMDs modelled; is there ONE Order, NDC, fare families, continuous pricing, RBD inventory?

### Takeaway

The record of truth is a single-flight PNR-style `bookings` row with 13-digit locally generated ticket numbers on `passengers`; an NDC-shaped `ndc_offers`/`ndc_orders`/`retail_offers` layer sits on top as a view, and ADR 0001 (status: Proposed, "Nothing in this document is implemented") plans the move to an order-owned model. Inventory is two cabin buckets per flight (`economyAvailable`/`businessAvailable`); the RBD `fare_classes` table and ATPCO-style `fare_rules` exist but are not on the sale path.

### Cited Findings

- `bookings` table: `flightId` NOT NULL (single flight), `bookingReference` and `pnr` both 6-char unique, `status` enum of 4 values (pending/confirmed/cancelled/completed), `paymentStatus` 4 values, `totalAmount` int "SAR cents", `cabinClass` enum economy|business, `stripePaymentIntentId`/`stripeCheckoutSessionId`, `inventoryLockId`, `idempotencyKey`, `tenantId` nullable "during migration" — [drizzle/schema.ts:252-300](drizzle/schema.ts).
- `flights` table: `economySeats`, `businessSeats`, `economyPrice`, `businessPrice`, `economyAvailable`, `businessAvailable`; status enum scheduled/delayed/cancelled/completed; `aircraftType` free text — [drizzle/schema.ts:180-230](drizzle/schema.ts). Price selection in booking is `cabinClass === "economy" ? flight.economyPrice : flight.businessPrice` — [server/services/flights.service.ts:244](server/services/flights.service.ts).
- `passengers`: `ticketNumber varchar(13)` "IATA 13-digit ticket number", `seatNumber`, `passportNumber`, `passportExpiry` (DATETIME since migration 0056) — [drizzle/schema.ts](drizzle/schema.ts) passengers block. Ticket number generation comment: "Generate a local document reference (13 digits; not external IATA issuance)" — [server/services/eticket.service.ts:57-63](server/services/eticket.service.ts).
- No coupon model: `grep -c coupon drizzle/schema.ts` = 0 and 0 in `ticket-documents.service.ts` (also recorded as F2 "Missing" in [docs/PROJECT_GAP_AUDIT_2026-09.md](docs/PROJECT_GAP_AUDIT_2026-09.md) section 4).
- `booking_segments` exists ([drizzle/schema.ts:2544](drizzle/schema.ts)) and is written by multi-city; APIS and check-in were later made segment-aware (audit closure F15, F17 in [docs/audits/2026-09-15-audit-closure.md](docs/audits/2026-09-15-audit-closure.md)).
- NDC layer: `ndc_offers` ([drizzle/schema.ts:5085](drizzle/schema.ts)), `ndc_orders` with `orderId`, `offerId`, `bookingId` (nullable link), `passengers` JSON text, `ticketNumbers`/`emdNumbers` JSON text, status enum pending/confirmed/ticketed/partially_ticketed/changed/cancelled/refunded, `orderPayload` text, channel enum direct/ndc_aggregator/gds/ota/travel_agent — [drizzle/schema.ts:5162-5230](drizzle/schema.ts). `retail_offers` with SHA-256 content digest and `consumedBookingId` — [drizzle/schema.ts:227](drizzle/schema.ts), described in ADR 0001.
- ADR 0001 states: "Status: Proposed. Nothing in this document is implemented"; "`createOrder` in `ndc.service.ts` creates the booking and passengers first and then the order that points at `bookingId`. The order is therefore a view over the booking, not its source"; service delivery state per item "does not exist today as a first-class fact" — [docs/architecture/decisions/0001-order-as-record-of-truth.md:3-57](docs/architecture/decisions/0001-order-as-record-of-truth.md).
- NDC transport: `NDC_VERSION = "21.3"` and message type names (AirShopping, OfferPrice, OrderCreate) are used as internal labels; the September audit F36 records "NDC internal only (no XML/JSON 21.3 endpoints, no seller auth)" — [docs/PROJECT_GAP_AUDIT_2026-09.md](docs/PROJECT_GAP_AUDIT_2026-09.md) F36; no XML parser/serialiser import found in `ndc.service.ts` (grep for `XML|xml|fetch(` returned only comment/label hits).
- Fare families / RBD: `fare_classes` has `code varchar(2)` (Y, J, C...), `cabinClass` enum first/business/premium_economy/economy, `fareFamily` ("Flex", "Light", "Value"), `priority` "for nested availability", `basePriceMultiplier`, `seatsAllocated`, refundable/changeable/changeFee/baggage/mileage/seatSelection/lounge/priorityBoarding/meal attributes — [drizzle/schema.ts:4716-4775](drizzle/schema.ts). Consumers of `fareClasses` are only `fare-rules.service.ts`, `ndc.service.ts`, `contracts/fare-rules.ts` (grep). Audit F1: "no RBD/booking class on the sale path; `fare_classes` and nesting consumed only by their router" — status Stub.
- Taxes/fees: audit F5 "no taxes/fees/YQ-YR anywhere; `totalAmount` single number" — Missing ([docs/PROJECT_GAP_AUDIT_2026-09.md](docs/PROJECT_GAP_AUDIT_2026-09.md) F5).
- Continuous pricing: the only occurrence of "continuous pric" in the repo is the self-comparison table marking AIS ❌ — [docs/SYSTEM_COMPARISON.md:151](docs/SYSTEM_COMPARISON.md). Dynamic pricing exists as multipliers (A/B variants, segmentation, AI multiplier, demand forecasting) in [server/services/pricing/](server/services/pricing/); the one `TODO` in non-test server code is "Implement route-based seasonal pricing using Hijri calendar" — [server/services/pricing/dynamic-pricing.service.ts:439](server/services/pricing/dynamic-pricing.service.ts).
- Money authority: `financial_ledger` ([drizzle/schema.ts:1396](drizzle/schema.ts)); ADR 0001 says every settlement/refund appends to it in the same transaction as the inventory change via `booking-settlement.service.ts`.
- Inventory holds: `seat_holds` ([drizzle/schema.ts:1779](drizzle/schema.ts)), `inventory-lock.service.ts` (`createInventoryLock`, `convertLockToBooking`, `releaseExpiredLocks`, `extendLock`), `inventory-capacity.service.ts` (`availableSeatsExpression`, `countActiveHolds`), channel allocations (migration 0033 "channel_inventory_allocations", `hard_block`/`soft_block` at [drizzle/schema.ts:4860-4886](drizzle/schema.ts)); seat capacity frozen at cost ingest (PR #179 "freeze seat capacity at cost ingest").
- Multi-tenancy: `tenants` table ([drizzle/schema.ts:23](drizzle/schema.ts)); `tenantId` nullable on `flights`, `bookings`, `passengers`, `payments`; 23 non-test files in routers/services reference `tenantCondition|strictTenantCondition|tenantStamp|assertTenant` (grep). The gap analysis header (1 Oct 2026) says completeness "needs independent verification" — [docs/AIRLINE_SAAS_GAP_ANALYSIS.md:6](docs/AIRLINE_SAAS_GAP_ANALYSIS.md). Audit F27: no feature flags, metering or per-tenant plan/branding on `tenants`.
- Roles: users.role enum user/admin/super_admin/airline_admin/finance/ops/support — [drizzle/schema.ts:77-85](drizzle/schema.ts); corporate member roles admin/booker/traveler — [drizzle/schema.ts:2904](drizzle/schema.ts).

### Inferences

- The data model is a two-cabin, single-segment, SAR-only reservation system with an NDC/ONE-Order vocabulary layered as metadata; it is not an order-managed system and has no coupon lifecycle, no tax breakdown, and no RBD-based availability on the sale path.
- Because `ndc_orders.passengers`, `ticketNumbers` and `orderPayload` are JSON text columns, the NDC layer is a record of messages rather than a normalised order model.

### Gaps

- Whether `nested availability` logic in `fare-rules.service.ts:743-830` (audit reference) is exercised by any UI or job today was not traced.
- Multi-currency: `currency.service.ts` exists and throws `Unsupported currency` ([server/services/currency/currency.service.ts:359](server/services/currency/currency.service.ts)); audit F34 says FX "would call external API". Current FX source not verified.

## Key question 3: Which external integrations exist and which are mocked, isolated or blocked?

### Takeaway

Only Stripe (Checkout + signature-verified webhook), Resend email, Twilio SMS, Hotelbeds, the AWC weather bulletin source, an on-call dispatcher and an OTLP trace exporter have real outbound adapters, each with a disabled/sandbox/live mode; GDS, biometrics, kiosk/bag-drop hardware, APIS transmission, DCS dispatch, alternate payment providers, BSP settlement and flight-data feeds are either simulated behind the demo gate or declared blocked, and the worker can be started under `AIS_PROVIDER_BOUNDARY=isolated`, which refuses any live credential.
