# Portable Railway Connection Template v1.0.0

A standard-library-only generator for a **read-only staging connection proof**
from GitHub Actions. Requires Python 3.12+; no framework or application runtime
dependency. Node and Railway CLI are installed only by the manual connection job.

## Create a destination adoption

1. Copy the entire `templates/railway-connection` folder, including the workflow
   template and tests. It is self-contained and does not import AIS application code.
2. Copy `target.example.json` to a private working config such as `target.json`.
   Replace the two fixture UUIDs with independently observed project/environment
   IDs, the exact environment name, and a unique destination Actions secret name.
   The config contains identifiers and a **secret name only**, never a token value.
3. Keep `environment_purpose` equal to `staging`. If the actual environment name
   differs, verify its purpose from destination policy and explicitly set
   `allow_name_purpose_mismatch` to true. This is a reviewed binding to two exact
   IDs, not permission to operate on arbitrary production environments.
4. Generate files into a new directory, then review them in a destination PR:

```sh
python3 templates/railway-connection/install.py --config target.json --destination ./generated-project
python3 -m unittest discover -s generated-project/scripts/ci -p 'test_railway_connection.py' -v
```

The generator never calls a network API, installs credentials, deploys or migrates.
It refuses example IDs, existing output files and symlinked output paths. Copying
to an existing repository is allowed only where all six destination files are new.
For upgrades, generate into a fresh directory and review the diff; no overwrite
switch is provided. `railway-connection-manifest.json` records file SHA256 values.
If destination formatting changes files, rerun tests and recompute that manifest
before sealing it; generation hashes describe generated bytes, not future edits.

## Generated files

| File                                       | Purpose                                                  |
| ------------------------------------------ | -------------------------------------------------------- |
| `.github/railway-connection.json`          | Reviewed target binding and secret name                  |
| `.github/workflows/railway-connection.yml` | Offline PR contract and exact-main-SHA manual connection |
| `scripts/ci/railway_connection_verify.py`  | Native CLI JSON verifier and allowlisted receipt         |
| `scripts/ci/test_railway_connection.py`    | Offline negative and receipt tests                       |
| `docs/runbooks/RAILWAY_CONNECTION.md`      | This operational guide                                   |
| `railway-connection-manifest.json`         | File hashes and source lineage                           |

Review the three action pins against destination policy. CLI 5.63.1 and its native
JSON schema are pinned together. The template uses standard Ubuntu runner Python;
if destination policy pins Python separately, add its approved setup action.
Run the destination formatter and all required CI checks on the final PR head.

After merge, create a fresh **environment-scoped project token** directly in the
destination's Actions secret named in the config. The generator embeds that name
in the workflow; changing the config's secret name later requires regenerating
and reviewing the workflow too. Never reuse another project's token or supply an
account-wide token. Tokens are exposed only in the bounded status step, after
CLI installation and target validation. Raw files are withheld and cleaned;
only the receipt is uploaded for 14 days.

Manually run `Railway read-only connection proof` on `main`, with `expected_sha`
equal to the exact reviewed merged SHA. Require `CONNECTION_ONLY_PASS`, exact
target IDs, source SHA, verifier/config hashes, and all false runtime proof flags.
PR unit tests, template generation and OAuth plugin reads do not prove this path.
`canAccess` must be boolean true; missing or ambiguous native CLI edges fail closed.
The workflow cannot determine the scope of a wrongly supplied token from its
string alone: environment-scoped token provisioning remains an operator duty.

## Evidence boundaries and lineage

SAHOOL issue #1259 / source `ccf195395fc0369975366ad61722194709e01115`
provided the original parser and workflow pattern. AIS PR #201 merged at
`2f0786aa4bbb048b17a5b72095b20dd22657748c`; 33 local operational tests and six
PR workflows passed. Its subsequent Railway retries completed on that source:

- `ais-migrate`: deployment `3f9a5e3a-f35e-487e-ab44-0ae964b532b6`, PASS,
  journal 56, pending 0, tables 156/156.
- `ais-acceptance`: deployment `258003c6-1b54-4487-a6d5-517936b6714c`, completed,
  127 passed, 0 skipped, 0 provider calls, exit 0; disposable database removed.
- Web liveness was 200 and readiness was 503. No production-readiness claim.

These are AIS acceptance-runner observations, **not** proof of the separate
GitHub Actions project-token path. That receipt was still pending when this
template was prepared. The generalization is verified offline in a generated
second project; every real destination still needs its own live receipt.

This v1 intentionally excludes deployment, migration execution, DB acceptance,
OAuth restoration and production certification. Never trigger a migration or
acceptance runner as a connection check. Automatic Railway deployments may still
run when an existing repository is merged under its own autodeploy policy; this
template does not change that policy. Investigate a one-banner BUILD_IMAGE failure
using bounded build logs, compare build inputs and keep the exact source SHA.
A successful retry supports a transient-failure hypothesis; it does not identify
the root cause. A retry of a migrator or runner requires its own write authority.

## Resume and verification

Before resuming, inspect the destination PR/main SHA, target IDs, config and
manifest hashes. Reuse offline evidence only for unchanged content. Live receipts
apply only to their own source and target. Do not repeat successful migrations,
redeployments or acceptance runs to reconstruct missing context.

To verify generated-file hashes from the destination root:

```sh
python3 - <<'PY'
import hashlib, json
from pathlib import Path
manifest = json.loads(Path('railway-connection-manifest.json').read_text())
for name, expected in manifest['files'].items():
    if hashlib.sha256(Path(name).read_bytes()).hexdigest() != expected:
        raise SystemExit('HASH_MISMATCH: ' + name)
print('MANIFEST_PASS')
PY
```
